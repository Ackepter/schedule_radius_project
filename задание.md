# Разработка ПО для автоматического составления расписания центра детских занятий

## 1. Общая задача

Разработай полноценное веб-приложение для центра дополнительных занятий детей.

Главная задача программы — хранить информацию о детях, их занятиях и доступности, педагогах, кабинетах и ценах, а затем автоматически формировать оптимальное расписание на неделю.

Программа должна учитывать все ограничения и не допускать конфликтов между детьми, педагогами и кабинетами.

## КРИТИЧЕСКОЕ ТРЕБОВАНИЕ

**НЕ СОЗДАВАЙ АЛГОРИТМ АВТОМАТИЧЕСКОГО ФОРМИРОВАНИЯ ГРУПП.**

Группы не являются результатом оптимизации.

Если занятие групповое, его состав участников задается пользователем заранее.

Алгоритм расписания должен только определить, **когда и где будет проходить уже существующее занятие**.

То есть:

```text
Ребенок → индивидуальное занятие
```

или:

```text
Групповое занятие
├── Ребенок 1
├── Ребенок 2
├── Ребенок 3
└── Ребенок 4
```

Состав групп пользователь формирует самостоятельно.

Алгоритм не имеет права объединять детей в группы, менять состав групп или создавать новые группы.

# 2. Технологический стек

Используй следующий стек:

### Backend

* Python 3.12+
* FastAPI
* SQLAlchemy 2.x
* Pydantic
* Alembic
* PostgreSQL
* OR-Tools для оптимизации расписания

### Frontend

* React
* TypeScript
* Vite
* Material UI (MUI)

### Инфраструктура

* Docker
* Docker Compose

Архитектура должна быть разделена на frontend и backend.

```text
React + TypeScript
        ↓
     REST API
        ↓
FastAPI + Python
        ↓
   SQLAlchemy
        ↓
   PostgreSQL
```

Алгоритм оптимизации должен находиться на backend:

```text
FastAPI
   ↓
Schedule Service
   ↓
OR-Tools
   ↓
готовое расписание
```

# 3. Основные сущности

Спроектируй нормальную реляционную модель базы данных.

Основные сущности:

* Student — ребенок
* Parent — родитель/контакт
* Subject — направление/предмет
* Teacher — педагог
* Room — кабинет
* LessonRequest — требования ребенка к занятиям
* GroupLesson — групповое занятие
* IndividualLesson — индивидуальное занятие
* ScheduledLesson — занятие в расписании
* Availability — доступность
* Price — тарифы
* Schedule — недельное расписание

Не дублируй данные без необходимости.

Используй нормальные связи PostgreSQL.

# 4. Дети

Для каждого ребенка хранить:

* ФИО;
* дату рождения или возраст;
* информацию о родителе;
* контакт родителя;
* комментарий;
* активность ребенка.

Для каждого ребенка должна быть возможность задать одно или несколько требований на занятия.

Например:

```text
Иванов Иван

Математика
Тип: индивидуальное
Количество занятий: 2 раза в неделю
Продолжительность: 60 минут

Доступность:
Пн 15:00–19:00
Ср 15:00–19:00
Пт 16:00–20:00
```

Другой ребенок может иметь:

```text
Петров Петр

Английский
Тип: групповое
```

# 5. Требования ребенка к занятиям

Создай отдельную сущность LessonRequest.

Она должна содержать:

* ребенка;
* направление;
* тип занятия:

  * individual
  * group;
* желаемое количество занятий в неделю;
* продолжительность;
* доступные дни;
* доступные интервалы времени;
* предпочтительного педагога — необязательно;
* дополнительные пожелания;
* приоритет требования.

Важно: доступность должна быть достаточно гибкой.

Например:

```text
Понедельник
15:00–18:00

Среда
16:00–20:00

Суббота
10:00–14:00
```

---

# 6. Индивидуальные занятия

Индивидуальное занятие:

* принадлежит одному ребенку;
* имеет одного педагога;
* проходит в одном кабинете;
* имеет одно направление;
* имеет определенную продолжительность.

Пример:

```text
16:00–17:00
Математика
Иванов Иван
Педагог: Петрова Анна
Кабинет: №2
Индивидуальное
```

Алгоритм должен учитывать индивидуальное занятие как отдельную задачу.

---

# 7. Групповые занятия

Групповое занятие — это заранее созданное пользователем занятие с фиксированным составом детей.

Например:

```text
Группа "Математика 5 класс"

Участники:
- Иванов Иван
- Петров Петр
- Сидоров Алексей
- Смирнова Анна

Предмет:
Математика

Продолжительность:
60 минут

Максимальный размер:
6 человек
```

Пользователь сам добавляет детей в групповое занятие.

Программа НЕ должна:

* создавать группы автоматически;
* объединять детей;
* разделять группы;
* менять состав группы;
* искать подходящих детей для объединения.

Алгоритм должен воспринимать групповое занятие как единую сущность, у которой несколько участников.

При назначении времени необходимо проверить доступность **каждого участника группы**.

---

# 8. Педагоги

Для каждого педагога:

* ФИО;
* список направлений, которые он преподает;
* рабочие дни;
* рабочие часы;
* максимальная нагрузка;
* дополнительные ограничения;
* комментарий.

Например:

```text
Петрова Анна

Предметы:
Математика
Физика

Понедельник:
14:00–20:00

Среда:
14:00–20:00

Пятница:
15:00–20:00
```

Педагог не может одновременно вести два занятия.

---

# 9. Кабинеты

Для каждого кабинета:

* номер/название;
* вместимость;
* допустимые направления;
* рабочие дни;
* доступное время;
* дополнительные ограничения.

Например:

```text
Кабинет №1

Вместимость: 8

Разрешенные направления:
Математика
Русский язык

Пн–Пт:
09:00–21:00
```

Кабинет не может использоваться для двух занятий одновременно.

Кабинет должен подходить для направления занятия.

Вместимость кабинета должна быть не меньше количества участников группового занятия.

Для индивидуального занятия достаточно вместимости 1.

---

# 10. Направления

Создай сущность Subject.

Для каждого направления:

* название;
* описание;
* стандартная продолжительность;
* разрешенные кабинеты;
* педагоги, которые могут его вести;
* активность.

Например:

```text
Математика
Английский язык
Русский язык
Робототехника
Программирование
Рисование
```

---

# 11. Цены

Создай отдельную систему тарифов.

Цена должна зависеть от типа занятия.

### Индивидуальные

Например:

```text
Математика — 1000 ₽
Английский — 900 ₽
Робототехника — 1200 ₽
```

### Групповые

Стоимость может зависеть от количества участников.

Например:

```text
1 человек — 1000 ₽
2 человека — 800 ₽/человек
3 человека — 700 ₽/человек
4 человека — 600 ₽/человек
5 человек — 550 ₽/человек
6 человек — 500 ₽/человек
```

Цены должны храниться в базе данных и изменяться через интерфейс.

Не прописывай цены непосредственно в коде.

Для каждого занятия рассчитывай:

* цену для одного ребенка;
* общую стоимость занятия;
* предполагаемую недельную стоимость.

---

# 12. Доступность

Система должна иметь универсальную модель доступности.

Доступность может существовать для:

* ребенка;
* педагога;
* кабинета.

Пример:

```text
Понедельник
09:00–12:00
14:00–19:00
```

Необходимо учитывать интервалы, а не только отдельные часы.

Продолжительность занятия должна полностью помещаться в доступный интервал.

Например:

```text
Доступность:
16:00–17:30

Занятие:
60 минут
```

Можно поставить:

```text
16:00–17:00
16:30–17:30
```

Но нельзя:

```text
17:00–18:00
```

---

# 13. Алгоритм составления расписания

Используй Google OR-Tools.

Задача должна быть реализована как задача Constraint Programming / CP-SAT.

Алгоритм должен назначать каждому занятию:

```text
день недели
время начала
время окончания
педагога
кабинет
```

При этом для группового занятия все участники должны быть свободны.

---

# 14. Жесткие ограничения

Эти ограничения НЕЛЬЗЯ нарушать.

### Ребенок

Один ребенок не может находиться одновременно на двух занятиях.

### Педагог

Один педагог не может вести одновременно два занятия.

### Кабинет

Один кабинет не может использоваться одновременно двумя занятиями.

### Доступность

Занятие должно полностью находиться:

* в доступности ребенка;
* в доступности педагога;
* в доступности кабинета.

Для группового занятия это должно выполняться для каждого ребенка.

### Педагог

Педагог должен иметь право преподавать выбранное направление.

### Кабинет

Кабинет должен быть разрешен для выбранного направления.

### Вместимость

Количество участников группового занятия не должно превышать вместимость кабинета.

### Продолжительность

Продолжительность должна соответствовать настройкам занятия.

### Частота

Если ребенок должен заниматься два раза в неделю, алгоритм должен попытаться назначить два занятия.

Нельзя назначить ребенку больше занятий, чем предусмотрено его требованиями, без явного разрешения пользователя.

---

# 15. Мягкие ограничения

После выполнения жестких ограничений алгоритм должен оптимизировать расписание.

Используй целевую функцию.

Желательно:

### Приоритеты

1. Максимизировать количество полностью выполненных требований детей.
2. Учитывать предпочтительное время ребенка.
3. Учитывать предпочтительного педагога.
4. Равномерно распределять занятия ребенка по неделе.
5. Минимизировать слишком длинные окна между занятиями одного ребенка.
6. Минимизировать очень ранние и очень поздние занятия.
7. Равномерно распределять нагрузку педагогов.
8. Эффективно использовать кабинеты.
9. По возможности избегать слишком больших промежутков между занятиями педагога.

Все эти коэффициенты должны быть вынесены в настройки оптимизатора.

---

# 16. Если расписание невозможно составить

Это очень важно.

Если невозможно удовлетворить все требования, программа НЕ должна создавать расписание с нарушениями.

Например:

```text
Не удалось назначить:

Иванов Иван
Математика
2 занятия в неделю

Причина:
Подходящие педагоги доступны только:
Пн 17:00–18:00
Ср 17:00–18:00

Но в эти интервалы все подходящие кабинеты заняты.
```

Должен отображаться понятный отчет.

Показывать:

* какие занятия не удалось разместить;
* каких ресурсов не хватает;
* какие ограничения стали причиной;
* возможные варианты решения.

Например:

```text
Можно попробовать:

[Добавить педагога]
[Добавить кабинет]
[Расширить доступность]
[Изменить время]
[Уменьшить количество занятий]
```

### Расписание ребенка

# 20. Ручное редактирование

После автоматической генерации пользователь должен иметь возможность вручную изменить расписание.

Можно:

* перемещать занятие;
* менять время;
* менять педагога;
* менять кабинет;
* удалять занятие;
* изменять участников группового занятия.

Но при каждом изменении система должна проверять ограничения.

Например:

```text
Нельзя переместить занятие.

Причина:
Педагог Петрова Анна занята
с 17:00 до 18:00.
```

Или:

```text
Нельзя использовать кабинет №2.

Причина:
Кабинет не предназначен для робототехники.
```

# 26. Автоматический выбор педагога

Если для занятия педагог не выбран заранее, алгоритм может выбрать подходящего педагога.

Но только из педагогов, которые:

* преподают это направление;
* доступны в выбранное время;
* не заняты;
* подходят по другим ограничениям.

Если пользователь указал конкретного педагога как обязательного, менять его нельзя.

Если педагог указан как предпочтительный, но не обязательный, алгоритм может выбрать другого.

# 33. Тестирование

Обязательно написать тесты.

Минимальные сценарии:

### Тест 1

Два индивидуальных занятия одного ребенка не пересекаются.

### Тест 2

Один педагог не может вести два занятия одновременно.

### Тест 3

Один кабинет не может использоваться одновременно.

### Тест 4

Ребенок не может иметь два занятия одновременно.

### Тест 5

Групповое занятие учитывает доступность всех участников.

### Тест 6

Групповое занятие нельзя назначить в кабинет с недостаточной вместимостью.

### Тест 7

Педагог не может вести предмет, который он не преподает.

### Тест 8

Кабинет нельзя использовать для запрещенного направления.

### Тест 9

Занятие не выходит за пределы доступности.

### Тест 10

Если расписание невозможно составить, программа сообщает об этом, а не создает конфликтное расписание.

### Тест 11

В расписании могут одновременно существовать индивидуальные и групповые занятия.

### Тест 12

Алгоритм не изменяет состав групп.

# 37. Главное требование к результату

В результате должно получиться реально работающее приложение, а не демонстрационный макет.

Пользователь должен иметь возможность:

1. Добавить ребенка.
2. Добавить его доступность.
3. Указать необходимые занятия.
4. Добавить педагогов.
5. Добавить их рабочие часы.
6. Добавить кабинеты.
7. Настроить направления.
8. Настроить цены.
9. Создать заранее сформированные групповые занятия.
10. Запустить автоматическое составление расписания.
11. Получить расписание без конфликтов.
12. Увидеть причины невозможности размещения отдельных занятий.
13. Вручную изменить расписание.
14. Получить расписание конкретного ребенка.
15. Получить расписание педагога.
16. Получить расписание кабинета.
17. Рассчитать стоимость.
18. Экспортировать итоговое расписание в PNG/PDF/Excel.

## Абсолютные запреты

Не реализовывать:

* автоматическое объединение детей в группы;
* автоматическое разделение групп;
* изменение состава групп оптимизатором;
* назначение одного ребенка одновременно на два занятия;
* назначение педагога одновременно на несколько занятий;
* назначение кабинета одновременно нескольким занятиям;
* создание расписания с нарушением жестких ограничений.

**Главный приоритет проекта: корректность алгоритма расписания, а не количество визуальных функций.**
